항공 탐지 학습 노트

항공뷰에서 쓰러진 사람을 찾는 모델을 학습·평가할 때, 모르면 반드시 틀리는 개념들. 모든 수치는 이 프로젝트에서 직접 측정한 값이다.

모델 yolov8s_stage1_all 학습 11,615장 · 객체 18,132개 · 1클래스 2026-09

목차

  1. 기하 고도·화각·해상도는 변수 하나다
  2. 기하 성능은 서서히 안 떨어진다 — 절벽이 있다
  3. 학습 imgsz는 두 가지를 뜻한다
  4. 학습 크기 견고성은 증강이 만든다
  5. 데이터 분할은 배우·비행 단위로
  6. 데이터 우리 데이터는 크기가 지워져 있다
  7. 평가 평균은 격차를 숨긴다
  8. 평가 어떤 지표를 볼 것인가
  9. 평가 임계값은 F2로 고른다
  10. 학습 모델 크기는 데이터가 정한다
  11. 학습 학습률이 사전학습을 파괴한다
기하01

고도·화각·해상도는 변수 하나다

이 셋을 독립된 선택지로 두고 조합을 실험하면 시간을 버린다. 셋은 하나의 값을 조절하는 손잡이 세 개일 뿐이다.

지상 표본 거리 (GSD)
지상 폭 W = 2 × 고도 × tan(화각 ÷ 2) GSD = W ÷ 가로 픽셀수 사람 픽셀 = 실제 크기 ÷ GSD

모델이 보는 것은 결국 사람이 몇 픽셀이냐 하나다. 고도를 두 배로 올리든, 화각을 두 배로 넓히든, 해상도를 절반으로 줄이든 — 모델 입장에서는 같은 일이 벌어진다.

우리 프로젝트에서 화각(54°)과 센서 해상도(1920×1080)는 예산안으로 확정됐다. 그러니 실제 자유 변수는 고도 하나, 그리고 학습·추론에서 정하는 imgsz 하나뿐이다.

기하02

성능은 서서히 안 떨어진다 — 절벽이 있다

"고도를 올리면 조금씩 나빠지겠지"는 틀렸다. 넓은 구간에서 거의 변하지 않다가, 어느 지점에서 무너진다.

사람 픽셀 크기별 성능 · 실측
겨울 mAP50 여름 mAP50 아래 축 = 실기체(54°·1920px) 환산 고도

여름 기준으로 97px에서 36px까지 0.575 → 0.520, 겨우 8% 떨어진다. 그런데 24px에서 0.325로 37% 붕괴한다. 24픽셀 안에는 사람이라는 증거가 물리적으로 부족하다.

기준서의 "탐지 하한 20px"은 위험하다. 20px 근처는 이미 절벽 안쪽이다. 안전 하한은 36px로 잡아야 한다.

뒤집어 보면 좋은 소식이다. 우리 운용 고도 20~40m는 사람이 80~160px로 보이는 구간이라 성능 걱정 구간이 전혀 아니다. 고도를 올리면 통과 폭이 넓어져 같은 구역을 훨씬 빨리 훑는다.

학습03

imgsz는 두 가지를 뜻한다

센서 해상도와 추론 해상도는 다른 것이다. 우리 학습 이미지 원본은 1280×720인데 imgsz 960으로 학습했다. 즉 매 이미지를 0.75배로 줄여 넣었고, 선형 25%의 정보를 버렸다.

그 결과 객체의 26~32%가 64px 미만으로 들어갔다. imgsz 1280으로 올리면 이 비율이 0~12%로 떨어진다. VRAM 4GB에서는 불가능했던 실험이라 아직 못 해봤다.

학습 imgsz가 곡선의 중심을 정한다. 960으로 학습한 모델은 사람 73px 근처가 중심이고, 1280으로 학습하면 97px가 중심이 된다. 같은 데이터라도 절벽 위치가 달라진다 — 그래서 모델을 바꾸면 크기 곡선을 다시 재야 한다.

그리고 비교할 때는 평가 imgsz를 반드시 맞춰야 한다. 960으로 학습한 모델을 1280으로 평가하면 학습 조건과 달라져 숫자가 왜곡된다.

학습04

크기 견고성은 증강이 만든다

앞의 곡선이 넓은 구간에서 평평한 것은 모델이 똑똑해서가 아니라 학습 중에 이미 다양한 크기를 봤기 때문이다.

실제 적용된 증강
설정값효과
scale0.5매 스텝 0.5~1.5배 무작위 확대·축소
mosaic1.04장을 합쳐 크기·맥락 다양화
degrees10.0항공뷰는 방향이 일정하지 않다
close_mosaic10마지막 10에폭은 모자이크를 끈다

close_mosaic이 중요하다. 모자이크는 실제 추론에서 절대 나타나지 않는 합성 이미지라, 끝까지 켜두면 학습 분포와 추론 분포가 어긋난 채로 끝난다. 마지막 구간에서 꺼서 진짜 이미지로 마무리한다.

데이터05

분할은 배우·비행 단위로

영상에서 뽑은 데이터셋에서 프레임 단위로 무작위 분할하면 성능이 크게 부풀려진다. 연속 프레임은 서로 거의 같은 그림이라, 같은 장면이 학습과 검증 양쪽에 들어가기 때문이다. 모델이 일반화한 게 아니라 본 것을 기억한 것이다.

우리 분할 기준
데이터셋분할 단위이유
NOMAD배우(Actor)같은 사람이 양쪽에 없도록
WiSARD비행(flight)같은 촬영분이 양쪽에 없도록
폴더 이름이 곧 분할 키다. WiSARD의 200704_Baker_FLIR_IR_1 같은 이름을 바꾸면 train/val 분할과 촬영 월 판별이 함께 깨진다.
데이터06

우리 데이터는 크기가 지워져 있다

NOMAD 원본은 5472×3078이고 촬영 거리에 따라 사람이 27~233px로 제각각이다. 그대로 넣으면 추론 해상도로 축소될 때 뭉개진다. 그래서 nomad_prep.py가 사람 크기를 목표 픽셀(약 97px)로 맞춰 리샘플링한 뒤 잘라냈다.

결과적으로 10m에서 찍은 것과 30m에서 찍은 것의 사람 크기가 똑같아졌다 — 실측 97px 대 98px. 이것이 무엇을 뜻하는지 정확히 알아야 한다.

잴 수 있는 것 / 없는 것
질문가능
고도가 높아 작게 찍히면 성능이 떨어지나불가
같은 크기일 때 멀리서 찍은 게 불리한가가능

두 번째를 실제로 재봤다. 10m와 30m에서 mAP50 0.559 대 0.579 — 오히려 멀리서 찍은 쪽이 근소하게 높았고, 정밀도는 0.729 대 0.816으로 뚜렷이 좋았다.

즉 이 구간에서 광학 정보량 손실은 무시할 수준이다. 크기만 확보되면 고도는 올려도 된다.

평가07

평균은 격차를 숨긴다

전체 검증셋 하나로 mAP를 내면 어디서 실패하는지 알 수 없다. 도메인을 나눠 재야 한다.

도메인 분리 평가 · 실측
모델여름 mAP50겨울 mAP50쓰러진 사람
기성 VisDrone0.1330.5440.048
통합 (운용 중)0.6410.9220.531

여름과 겨울의 격차가 0.28이다. 평균만 봤다면 이 차이를 못 봤을 것이고, "여름이 약점"이라는 개선 방향도 못 잡았을 것이다.

사람이 0명인 검증셋도 쓸모가 있다. WiSARD 9월분 289장에는 사람이 없다. mAP는 항상 0.0으로 나오는데 고장이 아니다 — 오탐 측정 전용 도메인이다. "사람 없는 배경에서 몇 건이나 잘못 신고하는가"를 여기서 잰다.
평가08

어떤 지표를 볼 것인가

지표마다 재는 것이 다르다. 우리 용도에서 중요도가 같지 않다.

지표별 의미와 우선순위
지표재는 것우선순위
재현율실제 있는 사람 중 몇 %를 찾았나최우선
mAP50박스가 절반만 겹쳐도 인정한 종합 점수중요
정밀도신고한 것 중 몇 %가 진짜였나보조
mAP50-95박스 위치가 얼마나 정확한가낮음

재난 탐색에서 놓치는 것이 훨씬 비싼 오류다. 못 찾은 사람은 되돌릴 수 없지만, 잘못 신고한 것은 사람이 확인하면 그만이다. 그래서 재현율이 최우선이다.

mAP50-95는 박스가 몇 픽셀 어긋나는지를 본다. 우리는 탐지 위치를 3m 반경으로 병합해서 신고하므로, 박스 몇 픽셀 차이는 결과에 거의 영향이 없다.

평가09

임계값은 F2로 고른다

신뢰도 임계값을 낮추면 더 많이 찾지만 오탐도 는다. 어디서 끊을지를 F1으로 정하면 안 된다 — F1은 정밀도와 재현율을 같은 무게로 본다.

우리는 F2를 쓴다. 재현율에 2배 가중을 준 지표다. 그 최대 구간이 conf 0.10~0.15였고, 운용값으로 0.15를 택했다.

임계값을 0.25에서 0.15로 낮춘 결과
항목0.250.15판단
쓰러진 사람 발견0.5310.608+0.077 얻음
배경 오탐 (장당)0.720.99+0.27 잃음

늘어난 오탐은 추적기가 흡수한다. 한 프레임만 반짝하는 탐지는 3프레임 안에 폐기되므로 지도까지 올라가지 않는다.

학습10

모델 크기는 데이터가 정한다

"최신·최대 모델이 낫겠지"는 우리 상황에서 성립하지 않는다. 학습 데이터가 11,615장 · 객체 18,132개 · 클래스 1개다.

공개 벤치마크의 성능 차이는 COCO 80클래스를 감당하려고 만든 용량에서 나온다. 1클래스 소규모 데이터에서는 그 용량이 과적합 위험으로만 남는다.

속도도 변별력이 아니었다. RTX 4080 SUPER 실측에서 yolo11s 56.5 FPS, yolo11m 60.8 FPS — 연산량이 3.2배인데 더 빨랐다. 이 크기의 모델은 GPU가 놀고, 실제 시간은 전처리·NMS·파이썬 오버헤드가 잡아먹는다. 요건(5 FPS)의 9~12배라 정확도로만 고르면 된다.

판단 기준은 이렇게 잡는다. m이 s보다 뚜렷이 좋으면 용량이 도움이 된다는 신호이니 l도 볼 가치가 있다. 비슷하거나 나쁘면 용량은 이미 포화이고 더 키우는 것은 시간 낭비다.

학습11

학습률이 사전학습을 파괴한다

파인튜닝에서 학습률을 처음부터 학습할 때처럼 크게 주면, 사전학습으로 얻은 특징이 초기 몇 에폭 만에 망가진다. 파국적 망각(catastrophic forgetting)이다.

실제로 겪은 실패 · 자세 2클래스 시도
증상결과
기본 lr0 = 0.01로 파인튜닝박스 손실 1.2 → 1.9로 악화
쓰러짐 재현율0.153에 그침

여기서 얻은 구조적 교훈이 하나 더 있다. 잘 되는 탐지기를 건드려 클래스를 늘리는 것보다, 탐지기는 그대로 두고 분류기를 뒤에 붙이는 편이 안전하다. 겨울 mAP50 0.922를 낸 모델을 위험에 빠뜨리지 않는다.

중간 지표만 보고 중단하지 말 것. 한 학습에서 2에폭 0.551 → 3에폭 0.310으로 떨어졌다가 최종 0.606으로 회복한 적이 있다. 학습률 워밍업과 스케줄 때문에 초반 등락은 정상이다.

요약 — 실행 규칙

  • 기하고도·화각·해상도를 따로 실험하지 말 것. 사람 픽셀 크기 하나로 환원해서 보면 된다.
  • 고도안전 하한은 36px. 운용 고도 20~40m는 80~160px 구간이라 여유가 크다. 고도를 올리는 편이 탐색 속도에 이득이다.
  • 평가도메인을 나눠 재고, 재현율을 최우선으로 본다. 평가 imgsz는 학습값과 맞춘다.
  • 데이터배우·비행 단위 분할을 지킨다. 프레임 단위로 다시 섞으면 수치가 부풀려진다.
  • 모델데이터가 11,615장·1클래스다. 크게 갈수록 좋아진다는 보장이 없다. 재보고 정한다.
  • 기록모델을 바꾸면 크기 곡선을 다시 잰다. 학습 imgsz가 절벽 위치를 옮긴다.
