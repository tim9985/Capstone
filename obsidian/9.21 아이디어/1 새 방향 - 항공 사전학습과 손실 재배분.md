# 방향 1 — 항공 사전학습

## 발단

NOMAD 원논문 저자가 성능 저하의 1순위 원인으로
*"training data bias toward **ground views rather than aerial ones**"* 를 지목했다.
확인해 보니 **우리가 정확히 그 상태였다.**

| 학습 | 시작 가중치 |
|---|---|
| `fov_11m_1280_all` | `yolo11m.pt` (COCO) |
| `l1_11l_1280` | `yolo11l.pt` (COCO) |
| `v3a_11m_neg` (진행 중) | `yolo11m.pt` (COCO) |

> [!warning] 의식적인 결정이 아니었다
> 노트북 계보는 **공개 YOLOv8s-VisDrone → NOMAD+WiSARD → stage1_all** 로 항공 시점을 한 번 거쳤다 (`WEIGHTS.md`).
> 서버에서 YOLO11 로 바꾸며 **YOLO11용 VisDrone 가중치가 없어** COCO 에서 직접 출발하게 됐다.
> **아키텍처 교체의 부산물**이지 판단의 결과가 아니다.
> 그래서 "항공 사전학습을 잃은 손해" 를 **분리해서 잰 적이 없다.**

## 공개 가중치를 전수 조사했다 (HuggingFace `dronefreak` 100개)

직접 학습할 필요가 없었다 — **YOLO11 전 크기 VisDrone 가중치가 이미 공개돼 있다.**

| 모델 | imgsz | 에폭 | VisDrone val mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|
| yolov9e | 640 | 300 | **40.02** | **23.73** |
| yolov11x | 640 | 300 | 38.44 | 22.60 |
| yolov26x | 640 | 300 | 38.33 | 22.48 |
| yolov8x | 640 | 300 | 36.81 | 21.52 |
| rfdetr-medium | — | — | 36.82 | 20.14 |
| yolov26m | 640 | 300 | 36.67 | 21.22 |
| **yolov11m** ← 우리 아키텍처 | 640 | 300 | 36.35 | 21.02 |

라이선스 AGPL-3.0 (ultralytics 와 동일) · `best.pt` · `args.yaml` 공개.

> [!info] "COCO 안 거친" 모델은 사실상 없고, 있어도 우리에게 더 나쁘다
> 위 가중치들의 `args.yaml` 은 전부 `model: yolo11m.pt` · `pretrained: true` — **COCO → VisDrone** 이다.
>
> | | 장수 |
> |---|---:|
> | COCO | 118,000 |
> | VisDrone train | **6,471** (COCO 의 1/18) |
>
> 이 규모로 처음부터 백본을 학습하면 저수준 특징(모서리·질감)조차 안 잡힌다.
> 이 분야 표준이 `COCO → 항공 → 목표` 인 이유다.
> **NOMAD 저자의 지적은 "COCO 를 쓰지 마라" 가 아니라 "COCO 에서 바로 오지 마라" 다.**

> [!note] 원격탐사 기반모델(SatMAE · Scale-MAE · RVSA · MTP)은 우리 용도가 아니다
> 위성 수직 하향 · GSD 미터 단위(우리는 드론 30 m · GSD 1~2 cm) · 대상이 건물·차량·선박 ·
> ViT 백본이라 YOLO11 에 못 붙인다. DOTA 사전학습 OBB(`yolo11m-obb.pt`)도 클래스에 사람이 없다.

## imgsz 640 이 걸리는가 — 아마 아니다

동물원 25종이 **전부 640** 이다. 1280 이상은 **TPH-YOLOv5**(VisDrone 2021 챌린지 4위 · imgsz 1536) 하나뿐인데,
YOLOv5l 에 트랜스포머 헤드를 붙인 개조라 우리 파이프라인(`eval_tile.py` · TensorRT · ultralytics 8.4.102 고정)이 못 쓴다.

**그런데 YOLO 는 완전 합성곱이라 가중치 자체는 입력 크기와 무관하다.**
진짜 문제는 특징이 **어떤 px 크기에 맞춰졌는가** 인데:

| | 객체 크기 |
|---|---|
| VisDrone 원본 ~1360×765 → 640 (×0.47) | 보행자 **5~19 px** |
| 우리 1280 크롭 (1:1 배율) | 사람 **16~160 px** |

**640 사전학습이 본 객체가 오히려 우리보다 작다.** 우리 실패 구간(16~25 px)과 겹치거나 더 아래다 —
해상도 불일치가 손해가 아니라 **이득일 가능성**이 있다. 추측이므로 돌려서 가린다.

## 후보와 순서

| | 가중치 | 근거 | 비용 |
|---|---|---|---|
| **A** | `dronefreak/visdrone-yolov11m` (640) | 아키텍처 동일 · 파이프라인 그대로 · **단일 변수** | **0 + 13 h** |
| B | 우리가 1280 으로 VisDrone 직접 학습 | A 가 무효일 때 **해상도 탓인지** 가른다 | 3 + 13 h |
| C | `visdrone-yolov9e` (VisDrone 최강) | — | 아키텍처 변경 → NFR-V01 · TensorRT · 타일 전부 재검증 |

**A 부터.** C 는 지금 손대지 않는다 — 우리는 이미 "모델 확대는 손해"(11m→11l **상대 −3~−8 %**)를 겪었고,
아키텍처를 바꾸면 속도·엔진·타일 설정을 전부 다시 재야 한다.

```bash
# A — 공개 가중치에서 출발 (fov_11m 과 사전학습 하나만 다르다)
huggingface-cli download dronefreak/visdrone-yolov11m best.pt --local-dir weights/visdrone_11m
python train_person.py --stage 1 --data configs/data_fov.yaml \
    --weights weights/visdrone_11m/best.pt \
    --imgsz 1280 --batch 8 --close-mosaic 0 --optimizer SGD --lr0 0.01 \
    --scale 0.3 --translate 0.15 --name vd_11m --epochs 30
```

## 더 싼 선행 확인 (10분)

본 실험 전에 **COCO 원본 `yolo11m.pt` 를 우리 시험셋에 그대로** 돌려 본다.

- 가림 지형 재현율@0.15 이 **0.05 수준** → 사전학습 기여가 거의 없다 = 항공 사전학습 여지가 크다
- **0.20 수준** → COCO 도 꽤 안다 = 이득이 작을 수 있다

# 방향 2 — 손실 가중치 재배분

`box 7.5 / cls 0.5 / dfl 1.5` 는 ultralytics 기본값이고 **COCO 80클래스·큰 객체** 기준으로 맞춰진 값이다.
우리는 1클래스 · 초소형 · 배경 혼동이 전부다. 같은 배분이 맞을 이유가 없다.

## 우리가 잰 것

가림 지형 시험셋 · 각 칸 40장 · **가중치 적용 후**

| 대상 크기 | box | cls | dfl | 합 |
|---|---:|---:|---:|---:|
| 18 px | 3.755 | **5.174** | 1.868 | 10.798 |
| 34 px | 3.156 | 4.090 | 1.896 | 9.142 |
| 71 px | 2.340 | 3.361 | 1.913 | 7.614 |
| 106 px | 2.236 | 2.395 | 1.724 | 6.356 |
| **106 → 18 증가 (상대)** | +68 % | **+116 %** | +8 % | +70 % |

가중치를 걷어내면 18 px 에서 **raw cls = 10.35** · raw box = 0.50 · raw dfl = 1.25.
`cls` 0.5 가 큰 값을 눌러 놓고 `box` 7.5 가 작은 값을 키워 놓은 구조다.

> [!warning] "손실이 크니 가중치를 올려라" 는 자동으로 성립하지 않는다
> 손실이 크다는 건 **줄일 수 없는 항**이라는 뜻일 수도 있다.
>
> **진짜 근거는 실패 양상이다** — 정밀도@0.15 **0.685** / 재현율@0.15 **0.391**.
> 오탐이 넘치는 게 아니라 **진짜 사람에게 낮은 점수를 주고 있다.** 분류 문제지 위치 문제가 아니다.

문헌 근거: Psych-Occlusion 은 모델·데이터를 안 건드리고 **손실만 바꿔** 가림 성능을 올렸다.
사람이 수색할 때 박스를 맞추려 하지 않고 **위치만 본다**는 시각심리 실험을 반영해 중심 좌표를 우선했다.
우리도 같다 — **운영자가 스냅샷으로 판단**(UC-0705)하고 채점이 **IoU 0.5** 라 박스 정밀도의 운용 가치가 낮다.

## 후보

| | box | cls | dfl | 성격 |
|---|---:|---:|---:|---|
| 현재 | 7.5 | 0.5 | 1.5 | ultralytics 기본 |
| **A (보수)** | 7.5 | **1.0** | 1.5 | cls 만 2배 — **단일 변수** |
| B (재균형) | **5.0** | **1.0** | 1.5 | 박스 정밀도를 덜 본다 |

**A 부터.** B 는 두 개를 같이 바꿔 원인이 안 갈린다. A 가 들으면 B 로 더 가고, 없으면 B 도 안 할 근거가 생긴다.

> [!danger] `best.pt` 선정과 충돌한다
> `fitness = mAP50-95` 라 **박스가 빡빡해야 점수가 나온다** (8.4.102 · `w=[0,0,0,1]`).
> box 를 낮추면 mAP50-95 는 떨어지는데 AP50·재현율은 오를 수 있고, **엉뚱한 에폭이 best.pt 로 뽑힌다.**
> · 대응: **`best.pt` 와 `last.pt` 를 둘 다 평가**한다
> · fitness 자체를 mAP50 으로 바꾸는 건 **별도 변수**라 같이 건드리지 않는다 → [[fitness와 조기 종료]]

구현: `train_person.py` 에 `--box --cls --dfl` 옵션 추가 (`--translate` 때와 같은 방식).

```bash
python train_person.py --stage 1 --data configs/data_fov.yaml --weights yolo11m.pt \
    --imgsz 1280 --batch 8 --close-mosaic 0 --optimizer SGD --lr0 0.01 \
    --scale 0.3 --translate 0.15 --cls 1.0 --name loss_a_11m --epochs 30
```
