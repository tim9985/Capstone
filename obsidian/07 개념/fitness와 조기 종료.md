> [!abstract] 한 줄
> Ultralytics 는 mAP50 이 아니라 **fitness** 로 최고 에폭을 고르고 학습을 멈춘다.

```
fitness = mAP50-95        ← 설치본 ultralytics 8.4.102 (utils/metrics.py · w = [0, 0, 0, 1])
```

> [!warning] 09-15 정정 — 옛 공식이었다
> 이 노트와 `CLAUDE.md` · SERVER_PROGRESS 가 쓰던 `0.1 × mAP50 + 0.9 × mAP50-95` 는 **옛 버전 공식**이다. 서버 설치본(09-10 설치 뒤 그대로)은 **mAP50-95 만** 본다.
> M1 · M2 의 best 22에폭은 두 공식에서 같아 결과는 그대로. 다만 옛 공식으로 적은 "fitness" 수치(예: 0.3816)는 실제 기준값이 아니다. `train_status.py` 는 09-15 에 고쳤다.

| 지표 | 뜻 |
|---|---|
| **mAP50** | 박스가 절반(IoU 0.5)만 겹쳐도 정답 — "찾았나" |
| **mAP50-95** | IoU 0.5~0.95 평균 — "정확히 감쌌나" |
| **fitness** | = mAP50-95 |

## 그래서 생기는 일

- mAP50 이 오르는데 patience 가 줄어든다 → mAP50-95 가 정체라서
- `best.pt` 가 mAP50 최고 에폭이 아닐 수 있다 — 우리 목표(NFR-V03)는 **AP50** 이라 어긋날 수 있다 → [[9.15 성능 올리기]] ②
  - 9차: best 는 **27 에폭 fitness 0.3684** (옛 공식으로 적은 값)

## 조기 종료

- `patience 10` = fitness 가 10 에폭 동안 안 오르면 멈춤
- 초반 2~4 에폭 하락은 **warmup** 탓 — 여기서 판단하지 말 것

## 박스 손실 · 클래스 손실

| 손실 | 뜻 |
|---|---|
| `box_loss` | 박스 위치·크기가 얼마나 틀렸나 |
| `cls_loss` | 클래스(사람/쓰러짐)를 얼마나 틀렸나 |
| `dfl_loss` | 박스 경계 분포를 얼마나 틀렸나 |
